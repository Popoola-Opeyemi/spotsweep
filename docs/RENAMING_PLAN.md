## 2. Code changes

### Cargo / crate

- `Cargo.toml`: package `spotsweep`, binary `spotsweep`, version `0.3.0`,
  repository/homepage adjusted to the new GitHub name.
- `src/main.rs`: call `spotsweep::run()`.
- `Cargo.lock`: regenerated by Cargo.
- All source doc comments, CLI strings, error messages, examples and clap
  `name`/about text use `spotsweep` / `SpotSweep`.

Spotlight API integration, scanner rules, FSEvents, reconciliation and SQLite
schema are not changed.

### Paths and environment

`src/paths.rs` becomes the single source of truth:

- `APP_NAME = "SpotSweep"`
- `DB_FILENAME = "spotsweep.db"`
- `LAUNCH_AGENT_LABEL = "com.spotsweep.agent"`
- new env vars `SPOTSWEEP_DATA_DIR`, `SPOTSWEEP_CONFIG`,
  `SPOTSWEEP_LAUNCH_AGENTS_DIR`.
- legacy env vars are still read as fallbacks.
- `AppPaths` exposes optional legacy locations:
  `legacy_data_dir`, `legacy_db_path`, `legacy_config_path`,
  `legacy_logs_dir`, `legacy_plist_path`, `legacy_launch_agent_label`.
- Default paths use `SpotSweep` / `spotsweep.db` / `~/Library/Logs/SpotSweep`.
- Custom `--data-dir` keeps logs under `<data>/logs` as before.

### Data migration

New module `src/migration.rs`.

Trigger: before any config/database initialization, in `cli::run` for CLI
commands and at the start of `daemon::run`. Only runs when using the default
Application Support location. Custom data directories are not auto-migrated;
the migration function accepts explicit paths for tests.

Safety algorithm:

1. Detect old data only if the old directory exists and has a database,
   configuration, exports, or other meaningful data.
2. If both old and new directories contain meaningful data, stop with a
   conflict. Nothing is written. The error prints both paths and recovery
   instructions.
3. Create a staging directory beside the new data directory:
   `.spotsweep-migration-<pid>-<timestamp>`.
4. Recursively copy old data into staging:
   - preserve mode bits;
   - recreate symlinks as symlinks;
   - copy files byte-for-byte.
5. Rename `state.sqlite3` to `spotsweep.db` inside staging, and rename the
   `-wal`, `-shm` and `-journal` sidecars so SQLite can recover a live WAL.
6. Validate the staged database read-only:
   - `PRAGMA integrity_check` must return `ok`;
   - `PRAGMA user_version` must not be newer than this binary;
   - required tables (`directories`, `meta`) must exist.
   If validation fails, delete staging and leave old data untouched.
7. Write `.spotsweep-migration.json` in staging with source, backup path and
   timestamp. This makes an interrupted migration detectable.
8. Rename staging to the new data directory. The new directory keeps the
   migration marker until the old directory is safely backed up.
9. Rename the old data directory to
   `~/Library/Application Support/SpotlightDevExclusions.backup-<timestamp>`.
10. Remove the marker. The backup remains for manual recovery.

Interrupted migration recovery:

- If `.spotsweep-migration.json` exists and the old directory still exists,
  validate the new database, move the old directory to the recorded backup,
  and remove the marker.
- If the marker exists and the old directory is gone, validate the new
  database and remove the marker.
- If the new directory exists without a marker and the old directory also has
  data, report a conflict; never overwrite either.

Logs:

- Copy old logs into `~/Library/Logs/SpotSweep` only if the new log directory
  has no log files. Old logs are left in place as part of the old backup story.
- Report copied/skipped logs in the migration report.

Idempotence:

- Once `spotsweep.db` exists in the new directory, migration is a no-op.
- The old directory is renamed, so a second run sees no old data unless the
  user restores a backup.

### LaunchAgent migration

- New label `com.spotsweep.agent`, new plist path.
- `launchagent` tracks both new and legacy targets.
- `install`/`restart`:
  1. boot out new and legacy labels;
  2. write the new plist;
  3. bootstrap the new agent with the existing retry logic;
  4. remove the legacy plist only after the new agent is confirmed loaded.
- `start`/`stop`/`uninstall` also boot out the legacy label so two daemons
  cannot run.
- `status` reports the new service and exposes legacy installed/loaded flags.
- `uninstall` removes both plists and unloads both labels.
- The old agent's `ProgramArguments` are not reused; the new plist points at
  `spotsweep` and the new data/config/log paths.

### Scripts and distribution

- `scripts/build-release.sh`: builds `spotsweep`, universal + per-arch
  artifacts named `spotsweep-*`.
- `scripts/install-release.sh`: downloads `spotsweep-macos-universal.zip`;
  repository is configurable via `REPOSITORY`; default is the new GitHub name.
- `scripts/install.sh`, `install-binary.sh`, `update.sh`, `uninstall.sh`:
  new paths, binary, labels, DB filename and migration cleanup. They detect
  and remove the old binary/agent after the new install succeeds.
- `scripts/update-formula-sha.sh`: updates `Formula/spotsweep.rb` and new
  release asset.
- `Formula/spotsweep.rb`: class `Spotsweep`, `bin.install "spotsweep"`,
  service runs `spotsweep daemon`, log path `var/log/spotsweep.log`.
- `.github/workflows/release.yml`: uploads new asset names. GitHub repository
  rename remains a manual GitHub-side action; workflow uses `github.repository`.
- README install section:
  - `brew install spotsweep`
  - curl URL for `spotsweep`
  - build output `target/release/spotsweep`
  - migration section for existing users.

## 3. Backward compatibility and breaking changes

- Existing data is migrated automatically at first launch.
- Existing LaunchAgent is unloaded and removed after the new agent starts.
- Existing binary can remain until installers remove it; installers attempt
  cleanup after successful new install.
- Old environment variables remain accepted as fallbacks.
- Old CLI command `spotlight-dev` is not kept as an alias. Document the
  breaking change and provide the new `spotsweep` command. This avoids keeping
  two differently named executables and two service paths.
- Old Homebrew formula: user must run
  `brew uninstall spotlight-dev-exclusions` before/after installing
  `spotsweep`; document this. The new installer cannot safely uninstall a
  Homebrew package.
- GitHub repository rename is manual: rename `spotlight-dev-exclusions` to
  `spotsweep` in GitHub settings, update the tap repository and formula URL.

## 4. Tests

Add unit/integration tests for:

- data migration success (DB rows preserved, DB renamed, backup exists);
- permission preservation;
- idempotent second migration;
- conflict when both old and new data exist;
- interrupted migration marker recovery;
- invalid/corrupt old DB leaves old data untouched;
- log copy behavior;
- CLI name and help output (`spotsweep`, no `spotlight-dev`);
- release artifact names;
- Homebrew formula name/binary/service;
- LaunchAgent label constants and legacy cleanup logic;
- existing full suite.

Verification commands:

```bash

cargo clippy --all-targets -- -D warnings
cargo test
cargo build
cargo build --release
cargo run -- --help
./target/debug/spotsweep --help
```

Repository-wide search afterwards for old identifiers, allowing only migration
code, this plan, README migration section, historical nohog references and
tests that intentionally mention old paths.

## 5. Manual GitHub/Homebrew actions

1. Rename the GitHub repository `spotlight-dev-exclusions` → `spotsweep`.
2. Update the tap repository name/URL if it is separate.
3. Publish a `v0.3.0` release with the new assets.
4. Update the Homebrew tap formula from `Formula/spotsweep.rb` (or copy it to
   the tap repo).
5. Existing Homebrew users should run:

   ```bash
   brew uninstall spotlight-dev-exclusions
   brew install spotsweep
   brew services start spotsweep
   ```

   The first `spotsweep` command migrates data and the new service install
   removes the old LaunchAgent.
